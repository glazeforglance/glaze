# Releasing Glaze

A short guide for maintainers. Releases are driven by Git tags: pushing `vX.Y.Z` runs the
[Release workflow](.github/workflows/release.yml), which builds the multi-arch image, pushes it to
`ghcr.io/glazeforglance/glaze` and creates the GitHub Release from CHANGELOG.md.

## Versioning

Glaze follows [Semantic Versioning](https://semver.org/). While the version is below 1.0:

- `0.x.Y` (patch) is for fixes;
- `0.X.0` (minor) is for new features or breaking changes.

Pre-releases are `X.Y.Z-rc.N`. They don't get the `latest` image tag and are marked as a
pre-release on GitHub.

## Checklist

1. `main` is clean and CI is green.
2. Every user-facing change is under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md).
3. If the UI changed, run `pnpm build` and `pnpm screenshots` and commit the new images in
   `docs/screenshots/` (needs `pnpm exec playwright install chromium` once; set `GLANCE_BIN` for
   the live preview shot).
4. `pnpm release:prepare X.Y.Z`: sets the version in every `package.json`, dates the
   CHANGELOG section and updates its links. It also refreshes the translation status table in
   [TRANSLATING.md](TRANSLATING.md), so translations merged from Weblate show up in the release,
   and prints which languages changed (e.g. `fil 0% → 42%`). It refuses a dirty tree, another
   branch than `main`, a version that isn't higher, an empty Unreleased section, or translation
   files with invalid JSON or broken placeholders (an incomplete language is fine).
5. Review the diff.
6. `git commit -am "chore(release): vX.Y.Z"`
7. `git push`
8. Wait for CI.
9. `git tag -a vX.Y.Z -m "Glaze vX.Y.Z"`
10. `git push origin vX.Y.Z`
11. Watch the Release workflow in Actions.
12. Verify the image tags on GHCR (`X.Y.Z`, `X.Y`, `latest`) and the GitHub Release.
13. Update your own deployment.

## What the Release workflow checks

- The tag must match `version` in the root `package.json` (`v0.1.2` ↔ `"0.1.2"`).
- CHANGELOG.md must have a `## [X.Y.Z]` section; its text becomes the release notes.

## When the Release workflow fails after the tag is pushed

1. Fix the problem on `main` (commit, push, wait for CI).
2. Delete the tag locally and remotely:

   ```bash
   git tag -d vX.Y.Z
   git push origin :refs/tags/vX.Y.Z
   ```
3. Delete the draft GitHub Release if one exists.
4. Tag again (steps 9–10 above).

If images were already pushed for that tag, prefer releasing `X.Y.Z+1` over re-using the tag:
people may already have pulled the first image.

## Translations

The status table in [TRANSLATING.md](TRANSLATING.md) is refreshed by
`pnpm release:prepare` (step 4 above), and `git commit -am` includes it. Weblate's
pull requests don't touch it; `pnpm i18n --check` only prints a note when it lags
behind, so those pull requests never fail on it. To refresh it between releases,
run `pnpm i18n --write`.

## Weblate setup

Translations live on [Hosted Weblate](https://hosted.weblate.org/projects/glaze/)
(free for open-source projects; apply under **Add new translation project**).
Create one project, **glaze**, with two components that share the repository.

### Component `app` (the interface)

| Setting                        | Value                                           |
| ------------------------------ | ----------------------------------------------- |
| Component name / slug          | `app`                                           |
| Source code repository         | `https://github.com/glazeforglance/glaze.git`   |
| Repository branch              | `main`                                          |
| File format                    | **i18next JSON file v4**                        |
| File mask                      | `apps/web/src/locales/*/app.json`               |
| Monolingual base language file | `apps/web/src/locales/en/app.json`              |
| Edit base file                 | off (English is edited in the code)             |
| Template for new translations  | `apps/web/src/locales/en/app.json`              |
| Source language                | English                                         |
| Language code style            | BCP style using hyphen as a separator (`pt-BR`) |

### Component `fields` (widget, page and setting texts)

The same settings, with `fields` instead of `app` in the name, the file mask
(`apps/web/src/locales/*/fields.json`), the base file and the template
(`apps/web/src/locales/en/fields.json`). Pick **Use the same repository as**
`glaze/app` (Weblate's shared-repository option, shown as a `weblate://glaze/app`
URL) so both components push together.

`en/fields.json` is generated by `pnpm schemas` from
`packages/schemas/overrides.ts`; never let Weblate edit it (keep **Edit base
file** off).

### Pushing through pull requests

- **Version control system:** GitHub pull request (Weblate pushes to a fork and
  opens a pull request against `main`; it needs Weblate's GitHub account to be
  allowed to fork, which is the default on Hosted Weblate).
- **Push branch:** leave empty; Weblate uses its own branch for the pull request.
- Our CI runs on the pull request, including `pnpm i18n --check`: broken
  placeholders or invalid JSON fail, missing translations don't.

### GitHub webhook

So Weblate sees new English strings right after a merge: in the repository,
**Settings → Webhooks → Add webhook**, payload URL
`https://hosted.weblate.org/hooks/github/`, content type `application/json`,
event **Just the push event**. (Weblate's docs list this URL under
"Notification hooks"; check there if it ever changes.)

### Recommended add-ons

In each component, **Manage → Add-ons**:

- **Cleanup translation files**: removes keys that no longer exist in English,
  so `pnpm i18n --check` doesn't keep warning about them.
- **Squash Git commits**: one commit per language (or per author, your choice)
  instead of one per string, which keeps the pull requests readable.
- **Customize JSON output**: set the indentation to match the repository
  (tabs). If your Weblate version only offers spaces, leave it at the default;
  `pnpm biome format --write .` fixes it after merging.

The placeholder check that matters (`{{name}}` kept as is) is Weblate's
**i18next interpolation** check. It is normally on for this file format; if it
isn't, add the `i18next-interpolation` flag under **Translation flags**.

I couldn't verify every label above against the current Weblate interface;
if one is named differently, the [Weblate docs on component
configuration](https://docs.weblate.org/en/latest/admin/projects.html) are
the reference.

## One-time organization setup

In the `glazeforglance` organization on GitHub:

- Make the GHCR package public: **Org → Packages → glaze → Package settings → Change visibility**.
- In the same package settings, under **Manage Actions access**, give the `glaze` repository **Write**.
- **Org Settings → Actions → General → Workflow permissions**: check that workflows may write packages.
